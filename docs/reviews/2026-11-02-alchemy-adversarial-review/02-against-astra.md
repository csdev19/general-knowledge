# Against migrating Kaipu's deploy pipeline to Alchemy now

## Position

Keep Wrangler as the sole Worker publisher, align its local/CI version, preserve the tagged-SHA verification and same-deploy secrets contract, and resolve whether console actually needs a release workflow (F3–F6, F13, U12). The intended end state is one understandable release path plus explicitly documented ownership of the few dashboard-managed resources, with a separate development Worker only when its requirement materializes (F7–F9). Alchemy has credible advantages for resource ownership and repeated environments; the strongest proposal is a carefully bounded hybrid, not a deploy-only substitution (F15, F19, U10). I oppose adopting even that hybrid today because it adds state and adoption work before the package establishes a repeated provisioning problem; I would reverse that judgment for demonstrated multi-environment needs and a successful migration rehearsal (F7–F8, F17, U1–U5, U10).

## Core arguments

1. **A replacement must reproduce the release contract, not merely upload a Worker.**
   - Evidence: production deploys use a pinned executable and `--secrets-file`; preview remains `versions upload`; the existing workaround follows actual version-resolution and post-preview secret failures (F3–F4). Verification runs on the tagged SHA, and candidate PRs dry-run the same script (F6). Alchemy equivalence for secrets, preview interaction, dry runs, local tools, and the web build is unresolved (U3–U4, U6).
   - Concrete cost: replacing `scripts/deploy-worker.sh` entails changing `release-api.yml`, `release-web.yml`, `pr-checks.yml`, and deciding the fate of `preview-web.yml`, plus proving the VITE build inputs and service bindings still work. This is inferred migration work from F1–F6 and U3–U6, not evidence that Alchemy cannot do it.
   - Strongest FOR answer: Alchemy becomes the only publisher and preserves the gates. That is coherent and does not violate the old hub rule (F9). It still owes those parity checks before it earns a production cutover. Deploy-only pays this cost while leaving dashboard R2/Access/DNS untouched (F7).

2. **The best environment benefit is ahead of the recorded requirement.**
   - Evidence: ADR 0007 deliberately chose manual Version URLs and defers a persistent environment until pre-production work needs writes (F8). Alchemy stages provide isolated names and state, but automatic per-stage service-binding resolution remains an inference in the package (F19). A front end bound to the production API can write to production (F22).
   - Concrete cost: a meaningful PR environment must select an API Worker, database credentials/data, bucket targets, and appropriate secrets; multiplying Worker names alone does not establish isolation. That requirement follows from the service-binding hazard, Neon database, S3-accessed buckets, and production secret source (F5, F7, F22).
   - Alchemy may organize this better, but the owner still has to define the data boundary. The currently documented need does not yet justify a PR-stage deploy/cleanup workflow (F8, F19, U10). Fewer than ten users is context, not a reason to discount production safety.

3. **Shared deployment state creates an operational obligation even in the narrow hybrid.**
   - Evidence: the Cloudflare backend requires a separately bootstrapped Worker/DO store; CI does not bootstrap it (F17, U5; [state documentation](https://alchemy.run/state-store)). Issue [#1194](https://github.com/alchemy-run/alchemy/issues/1194) reports account-wide state-store version coupling. Issue [#2604](https://github.com/alchemy-run/alchemy/issues/2604) is closed: it describes a failed existence check leading to overwritten state-store credentials (F17).
   - Concrete cost: someone owns bootstrap, backend credentials, recovery, and compatible CLI versions across stacks sharing the account. The proposed future reuse across products makes account-level coupling relevant, though its actual impact on Kaipu is unmeasured (F8, F17, U5).
   - Do not present #2604 as an unfixed current defect, or infer that beta.84 contains its later fix without release verification. It identifies a recovery scenario to rehearse. Another backend could avoid this particular singleton, but does not eliminate choosing and operating state (U5).

4. **Full IaC expands the change from shipping code to reconciling live infrastructure.**
   - Evidence: existing R2 buckets, preview Access, and the DNS zone are dashboard-managed (F7). Adoption reconciles declarations; resource removal can delete objects unless retained (F16; [resource lifecycle](https://alchemy.run/infrastructure-as-code/resource-lifecycle)). Preservation of omitted R2/domain/Access settings and uninterrupted Worker/domain adoption are untested (U1–U2).
   - Concrete cost: inventory the live configuration, declare the intended settings, rehearse adoption on equivalents, and inspect the proposed changes before taking ownership of `kaipu-bucket`, `kaipu-private-bucket`, and domain/access resources. The desktop also uploads into the public bucket, so this migration reaches beyond Worker releases (context §2, F7).
   - This is a bounded migration risk, not a prediction of data loss. Kaipu has no D1, KV, DO, Queues, or Containers to lose; D1 migration and Container replacement horror stories are not arguments about its current application (F2, F7). R2 preservation is applicable. Deploy-only avoids bucket adoption entirely, but also forfeits that central IaC benefit (F7, F16).

5. **Fast improvement is valuable; consuming it still needs deliberate upgrade verification.**
   - Evidence: the v2 line is explicitly breaking-change beta software with frequent releases (F14). Secret lifecycle issues are reported open, while the exact behavior needed by Kaipu is unresolved (F18, U3). No measured Cloudflare breakage frequency is available (U7).
   - Concrete cost: pin the deployment dependency and validate upgrades against pending previews, omitted/empty secrets, and state access before changing the production pipeline. These are specific acceptance cases motivated by F3–F4, F17–F18, not a generic demand for enterprise bureaucracy.
   - The owner's cadence argument is strong evidence of active maintenance, not measured compatibility (F14, U7). Wrangler also demonstrably failed here through pin drift (F3, F13). Aligning that pin addresses an observed cause with less scope than switching engines; the relative effort is a judgment, not a benchmark.

6. **Hybrid is defensible, but must earn a distinct ownership boundary.**
   - Evidence: Alchemy covers the unmanaged resources, whereas Wrangler auto-provisioning addresses bound KV/R2/D1/Queues (F7, F15, F20). The hub prohibits duplicate Worker publishers, not separate provisioning and publishing owners (F9).
   - Concrete cost: a hybrid needs a declaration entry point, persistent state, and a documented handoff of resource names/outputs to Wrangler. It must keep Worker configuration and secret ownership out of Alchemy if Wrangler owns those (inference from F9, F16 and U4–U5).
   - This is my strongest concession: recurring DNS/Access/R2 provisioning could justify hybrid without replacing releases. Today's package establishes manual ownership but no repeated provisioning toil, drift incident, or measured maintenance burden (F7, U10). My objection here is weaker than for deploy-only: supply that missing evidence and hybrid can win.

## What problem would Alchemy actually solve here?

The cheaper-fix assessments below are scope judgments, not measured implementation estimates.

- **Hand-managed R2, Access, and DNS:** real configuration ownership gap (F7). Alchemy can close it (F15). Wrangler auto-provisioning does not establish management of the existing S3-key buckets, their public domain, Access policies, or DNS zone (F7, F20). Inventorying and documenting them is the smallest immediate change, but is not equivalent to declarative reconciliation. If repeatability is required, this is the strongest reason to choose hybrid; the package does not prove which IaC tool is cheapest (U2, U10, F21).
- **No console deployment:** real absence, uncertain product intent (F1, U12). If console should ship, add its build/deploy workflow and release-please component using the existing release contract (F6; context §2). Alchemy cannot decide that policy; changing deploy engines is not necessary to fill this gap.
- **No persistent development environment:** currently an explicit decision rather than a broken feature (F8). One separate API/front-end environment can be expressed with distinct Worker names and bindings; Wrangler environments require explicit bindings rather than inheritance (F22). Alchemy becomes more attractive as these graphs multiply (F19, U10). Neither approach by itself settles Neon/S3 data isolation (F7).
- **Manual previews:** existing Version URLs already cover the accepted visual-review use case (F8). Workers Builds supplies branch previews and optional PR comments (F20); evaluate it only if automatic previews are wanted. It is not proven to preserve Kaipu's tagged-release gate as a production replacement (F6). Version previews are not isolated writable stacks, and the native Version URL option has a DO limitation (F20, F22). Alias behavior is not verified in this package; I do not claim aliases solve isolation.
- **Wrangler pin drift:** an observed defect with a targeted remedy: align workspace and CI pins, retaining explicit executable selection until verified (F3, F13). Alchemy trades that version-management problem for another dependency and backend compatibility surface (F14, F17).
- **Secret source split and historical bypass:** production GitHub Secrets and development Infisical remain distinct (F5). Keep that intentional contract or change it separately. Alchemy supports deployment-time configuration, including redacted values ([secrets documentation](https://alchemy.run/environments/secrets)); that does not prove additive, empty-dropped behavior after a preview upload (F4, U3). The old `.env` bypass was scaffold behavior, not proof of a v2 defect (F10).
- **Misleading deployment documentation:** correct the stale Alchemy claims and the stale hub description of Wrangler/action pinning (F3, F9, F11, F13). Adopting a tool to make obsolete docs true would not resolve the underlying ownership discipline.

## The Effect angle

Effect is a credible foundation for an infrastructure engine: typed failure channels, dependency injection, interruption, resource scopes, and retry policies suit orchestration. The hub describes those capabilities in `H/effect/why-effect.md:36–61`. That supports the owner's view that a rewrite could materially improve Alchemy; it does not demonstrate correct Cloudflare provider semantics or Kaipu-specific deployment parity (U1–U7).

Zero Effect in the application is not a veto (F12). The hub asks who owns the runtime and where the boundary sits (`H/effect/adoption-strategy.md:7–17`), and explicitly permits a library to keep Effect internal (`:23–32`). A deployment-only boundary could do the same for Kaipu. Runtime bundle impact is unverified, so I claim neither application bloat nor a necessary application rewrite (U8).

The actual cost to assess is what a release maintainer must understand to change configuration or diagnose failures. The hub discusses learning/debugging costs (`H/effect/why-effect.md:77–95`) and recommends adopting for a named capability (`H/effect/adoption-strategy.md:144–147`). Its warning about scripts (`H/effect/why-effect.md:137–155`) should not be stretched into a ban on using a sophisticated tool implemented with Effect. The hub has no tooling/IaC-specific conclusion (context §3). Evaluate the user-facing deployment experience; do not award or deduct points merely for the internal runtime.

## Steelman of the FOR side

1. **“Give every PR a coherent environment instead of stitching names and bindings together.”** Alchemy stages are a real abstraction for isolated state and resource names, with a documented creation/cleanup workflow (F19). This directly addresses the error of pointing a staging web app at production API (F22).
   **Rebuttal:** first establish a writable multi-environment requirement and demonstrate per-stage binding targets plus Neon/S3 isolation (F7–F8, F19, U10). Native previews satisfy today's narrower requirement (F8, F20). My rebuttal becomes weak once multiple writable environments are routinely needed; manual configuration can then be the greater burden.

2. **“Make the entire resource graph reviewable in one source of truth.”** Workers, buckets, DNS, Access, and their relationships can be declared instead of remembered across dashboard screens (F7, F15). This is a benefit Wrangler deploy alone does not provide.
   **Rebuttal:** full ownership must include an audited adoption plan and a state recovery procedure, and it does not automatically include Kaipu's external database or release-secret policy (F5, F7, F16–F17, U1–U5). Hybrid can capture much of this benefit while keeping the proven release contract. My rebuttal is weak if the owner can show repeated dashboard drift or provisioning work; the evidence package currently supplies neither measurement nor incident (F7, U10).

3. **“Use TypeScript composition instead of duplicated config; Effect makes the engine more disciplined.”** Expressing resource relationships in code is attractive as stages/resources grow, and Effect supplies useful orchestration primitives (F15, F19; `H/effect/why-effect.md:36–61`).
   **Rebuttal:** Kaipu currently has a small declared resource graph and unresolved compatibility with its local Wrangler tools and web build (F2, U4, U6). TypeScript does not itself establish omitted-setting preservation, correct physical names, or the release secret contract (F16, U1–U3). This wins when a concrete prototype reduces repeated configuration while passing those checks, not merely when its entry point looks cleaner.

## What would make me concede

- **Migration parity is demonstrated:** rehearsals resolve U1–U4 and U6 favorably, including domain continuity, explicit adoption diffs, unchanged retained settings, pending-preview secret behavior, and build/local-tool parity. That removes the principal objection to replacing the publisher; a measured workflow benefit must still justify doing it.
- **A real environment graph appears:** writable pre-production work or recurring PR environments reopen ADR 0007, and Alchemy demonstrates correctly isolated service bindings, database access, buckets, and secrets (F7–F8, F19, F22, U10). New D1/DO/Queues requirements would strengthen this case, though basic provisioning alone is already available in Wrangler (F20).
- **Resource ownership becomes recurring work:** evidence of dashboard drift, repeated setup, or an inability to reproduce Access/DNS/R2 settings makes a retained-resource hybrid cheaper to operate than the current process (F7, F15, U2, U10). I would concede hybrid before full deploy replacement.
- **The release/backend contract becomes predictable:** stable 2.x plus documented upgrade compatibility and a working recovery drill resolves the material concerns behind U5/U7 and F17. A stable label alone is insufficient; a pinned beta with equally convincing evidence could also qualify (F14, U7).
- **A bounded prototype shows an operational win:** compare the same Kaipu release/preview scenarios, including a failed deployment and recovery, and show fewer manual steps without weakening F4/F6. No such comparison is in the package; do not substitute issue counts, release frequency, or popularity for it (F14, U7).

## If the owner adopts anyway

These are proposed acceptance conditions, not claims that Alchemy already supplies each safeguard.

- Start on disposable resources and a non-production stage; settle U1–U6 before adopting live Workers or buckets. Keep physical names explicit and inspect every adoption change; do not apply `--adopt` broadly to resolve unexplained ownership conflicts (F16, U1–U2).
- Specify `retain` for production data resources and explicitly review policies for domains, Access, Workers, and the state backend. Review removal/replacement plans as operational changes. Retention does not prove omitted provider settings are preserved (F16, U2; [lifecycle documentation](https://alchemy.run/infrastructure-as-code/resource-lifecycle)).
- No `alchemy destroy` in CI during migration. If PR cleanup is later introduced, separately authorize and prove an ephemeral-only scope that cannot target production or shared state; do not copy the generic stage-cleanup example unchanged (F16, F19).
- Choose durable remote state, name its operator, bootstrap it outside CI, and rehearse restoration of both state and access to it. Record all stacks sharing the Cloudflare backend and pin compatible CLI versions together; verify the selected release contains required fixes (F17, U5).
- Preserve **secrets ship with the deploy**, additive updates, and empty-value dropping. Test the exact pending-version sequence that motivated the current contract, plus secret removal/rotation and log redaction. Use GitHub production values until a separate source migration is justified; no laptop `.env` fallback (F4–F5, F10, F18, U3).
- Keep tagged-SHA verification and equivalent candidate deploy validation; establish one production publisher after cutover (F6, F9). Document a controlled rollback procedure that first stops the new owner from reconciling the old publisher's changes (inference from F9, F16).
- For hybrid, state explicitly that Alchemy owns selected infrastructure and Wrangler owns Worker code/config/secrets; wire outputs deliberately and prohibit overlapping ownership. For full replacement, resolve local dev/types/preview workflows before removing `wrangler.jsonc` (F9, U4).
- Keep Effect confined to deployment tooling unless a separate application decision is made, and verify the runtime bundle boundary (F12, U8). Update stale deployment documentation at cutover so another reader cannot revive a second path (F10–F11).
