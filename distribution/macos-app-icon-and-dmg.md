# The app icon and the DMG install window (macOS)

_Making the download look finished: the icon geometry Apple never states in the asset catalog,
and how to get Finder's install window to open with your layout on a machine that has no Finder._

This is the layer where the build tool helps least. `xcodebuild`, `tauri build` and
`electron-builder` all hand you a working `.app`; none of them has an opinion about whether the
icon has the right margins or whether the disk image opens as a designed window. Both are just
files you commit, so the technique below is the same in every toolchain.

---

## Part 1 — The app icon

### The geometry is not the canvas

An asset catalog asks for a 1024×1024 PNG and says nothing else, which invites you to fill all
1024 pixels. Every system icon instead draws a **rounded square inside transparent margins**, and
macOS relies on that: the Dock, Launchpad and Finder add their own shadow and alignment assuming
the art stops short of the edge.

The working numbers, from Apple's macOS icon template:

| Value | Size |
| --- | --- |
| Canvas | 1024 × 1024, transparent |
| Rounded rect (the visible icon) | 824 × 824, centred — 100 px margin on each side |
| Corner radius | ~185 px on the 824 rect (the macOS "squircle" look) |

Compose the brand art **onto** that rounded rect, do not scale the art to the canvas. An icon that
fills the full 1024 reads as visibly larger and misaligned next to every other icon in the Dock —
which is exactly how a home-made app announces itself.

### The slots, and why there are fewer files than rows

macOS wants ten catalog entries but only seven images: each pixel size serves both as `1x` of one
logical size and `2x` of the one below it. Render seven PNGs and reference them twice.

```jsonc
// Assets.xcassets/AppIcon.appiconset/Contents.json
{ "filename": "icon_16.png",   "idiom": "mac", "scale": "1x", "size": "16x16" },
{ "filename": "icon_32.png",   "idiom": "mac", "scale": "2x", "size": "16x16" },
{ "filename": "icon_32.png",   "idiom": "mac", "scale": "1x", "size": "32x32" },
{ "filename": "icon_64.png",   "idiom": "mac", "scale": "2x", "size": "32x32" },
{ "filename": "icon_128.png",  "idiom": "mac", "scale": "1x", "size": "128x128" },
{ "filename": "icon_256.png",  "idiom": "mac", "scale": "2x", "size": "128x128" },
{ "filename": "icon_256.png",  "idiom": "mac", "scale": "1x", "size": "256x256" },
{ "filename": "icon_512.png",  "idiom": "mac", "scale": "2x", "size": "256x256" },
{ "filename": "icon_512.png",  "idiom": "mac", "scale": "1x", "size": "512x512" },
{ "filename": "icon_1024.png", "idiom": "mac", "scale": "2x", "size": "512x512" }
```

Tauri and electron-builder take a single source PNG (or `.icns`) and generate the rest — the
geometry rule above still applies to that source, because neither tool adds the margin for you.

### Script the rendering, or you will redraw it by hand

Brand art changes. If the icon is seven committed PNGs with no generator, every revision is a
manual export at seven sizes, and the version that ships drifts from the source file the designer
sent. Treat the icon like any other generated asset: **source art in the repo, one command that
renders every slot**, the same way menu-bar/tray marks are usually handled.

This is worth stating because it is the step most often skipped: in the project this doc is drawn
from, the menu bar marks are generated by a committed script while the app icon is seven committed
PNGs with no generator — so the marks survived two art revisions cheaply and the icon did not.

## Part 2 — The DMG install window

### What "a nice installer" actually is

There is no installer. A DMG is a disk image containing two things:

```text
<App>.dmg
├── <App>.app             the stapled app
└── Applications -> /Applications    a symlink
```

The "drag me there" window is **Finder's own icon view**, and everything that makes it look
designed — window size, icon positions, icon size, hidden toolbar, background picture — is stored
in a `.DS_Store` file at the root of the image. Nothing more.

### Capture the layout once, commit it, replay it forever

CI has no Finder to arrange icons in. So arrange them once on a human's machine, then commit the
result as a binary fixture.

1. Build a DMG locally, open it, arrange it in Finder: icon view, hide toolbar/sidebar/status bar,
   set the icon size, set the background picture, drag the two icons into place.
2. Close the window (Finder writes `.DS_Store` on close), then copy that `.DS_Store` out of the
   mounted image into the repo — e.g. `Config/dmg/DS_Store`, committed as a binary.
3. From then on, staging is a copy:

```bash
STAGE_DIR="$DIST_DIR/dmg-stage"
mkdir -p "$STAGE_DIR"
ditto "$APP_PATH" "$STAGE_DIR/$APP_NAME.app"
ln -s /Applications "$STAGE_DIR/Applications"

mkdir -p "$STAGE_DIR/.background"
cp "$REPO_ROOT/Config/dmg/background.png" "$STAGE_DIR/.background/background.png"
cp "$REPO_ROOT/Config/dmg/DS_Store"       "$STAGE_DIR/.DS_Store"

hdiutil create -volname "$APP_NAME" -srcfolder "$STAGE_DIR" -ov -format UDZO "$DMG_PATH"
```

`hdiutil` copies the staged tree verbatim, so the committed `.DS_Store` arrives intact and Finder
opens the image with the captured layout — on a headless runner, with no AppleScript and no Finder
automation.

The `.DS_Store` references the background by **path** (`.background/background.png`), not by
content. Redrawing the background image is therefore free: keep the filename and the committed
layout still applies.

### A worked set of values

Useful as a starting point; the only hard constraint is that the background must be exactly twice
the window in pixels.

| Thing | Value |
| --- | --- |
| Window bounds | `{{200, 462}, {600, 400}}` — 600 × 400 points |
| Background PNG | 1200 × 800 px @ 144 dpi (the @2x of that window) |
| Icon size | 128 px |
| App icon position | x 150, y 185 |
| `Applications` position | x 450, y 185 |
| Chrome | toolbar, sidebar and status bar all off |

### The trap: Finder draws icon labels in black

**As soon as a window has a background picture, Finder renders file labels in black — in both light
and dark appearance.** A dark, on-brand background therefore ships an install window where
"Applications" is nearly invisible, and it looks correct in every design tool you preview it in.

Design the DMG background on a **light** surface regardless of the app's own palette. This cost a
release to discover and a follow-up fix to correct: the dark v2 surface went out in one version and
was redrawn on the light palette in the next, same geometry, same committed layout.

### Sign and notarize the disk image itself

The stapled app inside is not enough — the container is also downloaded, also quarantined, and
also judged by Gatekeeper:

```bash
codesign --sign "Developer ID Application" --timestamp "$DMG_PATH"
xcrun notarytool submit "$DMG_PATH" --key ... --key-id ... --issuer ... --wait
xcrun stapler staple "$DMG_PATH"
xcrun stapler validate "$DMG_PATH"
spctl --assess --type open --context context:primary-signature --verbose "$DMG_PATH"
```

That last `spctl` line is the check worth keeping in CI: it asks the same question Gatekeeper asks
when a user double-clicks the download, so a regression fails the build instead of a user's first
launch.

## Checklist

- [ ] Art composed on the 824 rounded rect inside the 1024 canvas, not edge to edge
- [ ] Seven PNGs rendered by a committed script from committed source art
- [ ] Catalog references the seven files across the ten `1x`/`2x` slots
- [ ] DMG stages the app plus an `/Applications` symlink
- [ ] Finder layout captured once into a committed `.DS_Store`, background under `.background/`
- [ ] Background is light (black labels), and exactly 2× the window size in pixels
- [ ] DMG signed, notarized, stapled, and asserted with `spctl --type open`
